# cq 측정 이력 (v1–v10)

이 저장소(Build Week 버전, 2026-07-19~)보다 앞선 실험 기록이다. 원본은 별도 로컬 저장소
(`~/cq`, 태그 v1~v10, 2026-07-02)의 `HANDOFF.md`이고, 숫자는 원문 그대로 옮겼다.

## 출발점
quarkify(companyjupiter)의 "everything is a folder" 아이디어에서 시작해, 폴더 트리 대신
압축 인덱스 + 정확한 슬라이스로 재설계했다.

## 버전별 결과
| 버전 | 변경 | 결과 |
|---|---|---|
| v1 | 줄번호 인덱스 | raw 트리 그대로는 진다 |
| v2 | 정확한 슬라이싱(들여쓰기+괄호 균형) | |
| v3 | 이름 기반 타겟팅(`Class.method`) | |
| v4 | 인덱스 압축(L2) + 스코프 필터(테스트 제외) | |
| v5 | quarkify 실험에서 독립 도구 cq로 분리(MIT) | ~7.6x (프록시 측정) |
| v6 | 실제 API(gpt-5.4) 단발 A/B | input **8.04x** 절감 (22,557 → 2,805), 품질 유지 |
| v7 | 에이전트 자율탐색 실측 | **0.59x** (경로 불일치로 헛발질 11회 + 과탐색) |
| v8 | 경로 자동보정 | 헛발질 0, input 38K → 14K, **1.60x** ← 최고 기록 |
| v9 | 클래스 레벨 desc(docstring/시그니처) 힌트 | 16.7K / 1.35x, **실패** → 롤백 |
| v10 | 콜그래프 힌트 + 억제 문구 | 14.5K / 1.56x, **실패** → v8로 롤백 |

## 교훈
1. raw 트리 그대로는 진다. 압축 인덱스 + 정확 슬라이스가 이긴다.
2. 단발 8x는 이상적 상한이다. 자율탐색 실전은 ~1.6x (탐색 오버헤드).
3. "에이전트에 힌트 더 주기"(desc, 콜그래프)는 두 번 다 실패했다. 힌트 비용 ≈ 힌트로 아끼는 비용.
   과탐색은 도구 쪽 힌트로 못 잡는다 — 태스크/에이전트 지침 쪽 문제일 가능성.
4. 숫자는 항상 정직판으로 유지한다.

## 측정 방법과 한계
- 단발 A/B: input 토큰 실측 (gpt-5.4 Responses API).
- 자율탐색: cq를 function tool로 등록하고 에이전트 왕복 input 누적 측정.
- baseline: 관련 파일 통째 읽기 (`requests` 리다이렉트 태스크 = 22,557 토큰).
- ⚠️ `requests`(Python) 레포 하나로만 검증했다. 일반화는 미검증.
- ⚠️ 실제 작업에서 사용한 기록은 없다. → [dogfood-log.md](dogfood-log.md)

# 2026-09-24 에이전트 A/B (codex) — 탈락

위 v1~v10 기록과는 비교하지 않고 새로 측정했다. 판정은 측정 전에 고정한 기준으로 사용자가 내렸다.

## 설정
- 에이전트: `codex exec` 0.155.1, `gpt-5.6-luna`, reasoning effort `low`
- 격리: `--ephemeral --ignore-user-config --ignore-rules -s workspace-write`. 매 실행마다 레포를 새로 복사했다(`.git` 제외).
- **A군**: 에이전트 안내 파일 없음. **B군**: `AGENTS.md`로 cq 사용 안내(`index --level=L0` → `inspect`)
- 대상: GuardianAI `app.py` (2,316줄, 단일 파일 — cq에 유리하도록 고른 조건)
- 태스크 (판정은 AST로 함수만 추출해 실행)
  - t1 `cvss_label`: 0 미만 또는 10 초과이면 `ValueError`, 범위 안의 등급은 유지
  - t2 `RedTeamPDF.kv`: 값이 `None`이거나 `""`이면 `"-"`를 출력, 나머지(0 포함)는 유지
- 2 태스크 × 2군 × 3회 = 12회. A와 B를 번갈아 실행했다.
- 통과 기준(측정 전 고정): 주 지표 중앙값에서 B ≤ A × 0.8, B 성공률 ≥ A 성공률, B cq 호출률 ≥ 70%

## 결과 (중앙값)
| 태스크 | 군 | 주 지표 (비캐시 입력 + 출력) | 전체 입력 | 변동분* | 성공 | cq 호출 | 명령 수 |
|---|---|---|---|---|---|---|---|
| t1 | A | 15,815 | 81,538 | 1,051 | 3/3 | 0/3 | 4, 4, 4 |
| t1 | B | 15,214 (−3.8%) | 90,087 (+10%) | 1,463 | 3/3 | 3/3 | 5, 6, 5 |
| t2 | A | 15,418 | 90,826 | 1,023 | 3/3 | 0/3 | 6, 5, 4 |
| t2 | B | 17,785 (+15.4%) | 154,850 (+70%) | 1,857 | 3/3 | 3/3 | 10, 9, 7 |

\* 변동분 = 입력 − 캐시 읽기 − 캐시 쓰기 + 출력

판정: **두 태스크 모두 탈락.** 품질은 같았고(12/12 성공), cq는 매번 호출됐으므로 "결론 없음"이 아니라 효과 없음이다.

## 관찰
1. **A군은 원래 적게 읽는다.** 매번 `rg`로 위치를 찾고 `sed -n '510,580p'`처럼 범위만 읽었다.
   cq가 줄이려던 "파일 통째 읽기"가 현재 에이전트에는 없다. v1~v10의 baseline 가정이 틀렸던 것이다.
2. **B군은 cq를 쓰면서 `rg`도 병행했다.** 도구가 대체되지 않고 추가됐다(명령 수 증가).
3. **t2에서 대상을 잘못 짚었다.** `_safe`, `generate_pdf`는 최상위 함수인데 에이전트가
   `RedTeamPDF._safe`, `RedTeamPDF.generate_pdf`로 inspect하고 재시도했다. L0 인덱스가 클래스 메서드 목록
   바로 아래에 최상위 `fn:` 목록을 들여쓰기만 달리해서 붙이는 형식이라 혼동을 부른 것으로 보인다.

## 지표 설계 결함
주 지표 약 15K 중 약 14K가 캐시 쓰기, 즉 시스템 프롬프트 같은 고정 비용이었다. 탐색 방식으로
바뀌는 부분은 실행당 약 1K뿐이어서, 이 지표로는 20% 절감이 원래 거의 불가능했다.
다만 전체 입력과 변동분으로 봐도 B가 더 컸기 때문에 판정 방향은 바뀌지 않는다.

## 한계
- n=3, 모델 하나(luna low), 태스크 2개, 대조군 없음. 유의성은 주장하지 않는다.
- 결과는 "cq에 가장 유리한 조건"에서 나왔다. 그래서 부정적 결론은 오히려 무게가 있다.

## 결론
- 토큰 절감 주장은 실제 에이전트 기준으로 성립하지 않았다.
- README가 내세우는 "신뢰/출처" 주장(추측 금지, 출처 기록)은 이번에 검증하지 않았다.
- 원자료: `bench/results/2026-09-24T05-01-43-499Z/`, `bench/results/dryrun-1/` (실행별 지표와 요약만 있다. 대상 레포 GuardianAI가 공개본을 만들던 2026-10-03 당시 비공개였기 때문에 이벤트·stderr·diff 원본은 뺐다)

# 2026-10-03 재측정 — 큰 다중 파일 레포 (sqlglot) — 탈락

9/24 결과가 "cq에 유리한 조건(단일 파일)"에서 나왔다는 반론을 확인하려고, `rg`+`sed`에 불리한 조건으로 다시 쟀다.

## 설정 (9/24 대비 변경점만)
- 대상: `sqlglot` v27.0.0 (파이썬 75개 모듈, 약 54K줄, 5K줄 넘는 파일 3개). 고정 클론: `bench/tasks.sqlglot.json`
- 태스크: 프롬프트에 파일·심볼 이름 없이 동작만 적었다. 판정은 실제 transpile 결과와 기존 테스트로 했다(`bench/checks/sqlglot/`).
  - t3 `CBRT` → T-SQL `POWER(x, 1/3)` · t4 `BIT_COUNT`를 새 식 클래스로 추가하고 ClickHouse `bitCount` 대응(2개 파일) · t5 T-SQL `SPLIT_PART`가 결과에서 사라지는 버그
- 주 지표: **누적 전체 입력 + 출력**(캐시 읽기 포함). 9/24 지표 결함을 반영해 측정 전에 바꿨다.
- 통과 기준(측정 전 고정): B 중앙값 ≤ A × 0.8, B 성공률 ≥ A, B cq 호출률 ≥ 70%
- B군 안내: `bench/agents/cq.md`. 시험 실행에서 권유형 안내는 무시당했기 때문에(cq 호출 0회),
  "소스는 `cq inspect`로 읽을 것, `rg`는 위치 찾기에만"이라는 지시형으로 바꾼 뒤 본 측정을 했다.

## 결과 (중앙값, n=3)
| 태스크 | A | B | B/A | 성공 | cq 호출 |
|---|---|---|---|---|---|
| t3 | 379,674 | 373,200 | −1.7% | 3/3 · 3/3 | 0% · 100% |
| t4 | 293,926 | 436,589 | **+48.5%** | 3/3 · 3/3 | 0% · 100% |
| t5 | 249,425 | 331,340 | **+32.8%** | 3/3 · 3/3 | 0% · 100% |

판정: **세 태스크 모두 탈락.** 18회 모두 성공했고 cq도 매번 쓰였으므로, 이번에도 결론 없음이 아니라 효과 없음이다.

## 관찰
1. **큰 레포에서도 A군은 좁게 읽었다.** `rg -n`으로 줄 번호를 얻고 `sed -n 'a,bp'`로 수십 줄만 읽었다.
   9회 실행에서 `sed`/`cat` 출력은 합쳐서 약 73K자였다.
2. **B군은 슬라이스 단위가 너무 컸다.** cq는 심볼 단위로만 자를 수 있다. 그래서 `Generator`(31K자),
   `TestTSQL`(29K자)처럼 클래스를 통째로 inspect하는 일이 생겼다. `rg`의 매칭 줄 단위 정밀도를 따라가지 못했다.
3. **도구가 대체되지 않고 추가됐다(9/24과 같다).** B군도 `rg`를 20회 썼고, 명령 수 중앙값은 A 9회, B 11회였다.
4. 실행 시간도 B가 길었다(중앙값 A 57초, B 73초).

## 결론
- 단일 파일(9/24)에서도, 큰 다중 파일 레포(10/3)에서도 토큰 절감은 없었다. 오히려 늘었다.
  "인덱스 + 심볼 슬라이스"가 `rg -n` + 줄 범위 읽기보다 싸다는 전제는 현재 에이전트에서 성립하지 않는다.
- 한계: 모델 하나(luna low), 레포 하나(모델이 잘 아는 sqlglot), n=3. 유의성은 주장하지 않는다.
- 원자료: `bench/results/2026-10-03-sqlglot/`, 시험 실행 `bench/results/dryrun-sqlglot/`
